# Private Dependency Memory: Failing-Case-Derived Design

## Scope

This document derives the first dependency-memory prototype from the eight dependency-fault cases in the 20-task baseline: Tasks 2, 3, 4, 7, 9, 12, 17, and 19.

The immediate research questions are:

1. From which events should a dependency memory item be generated?
2. How should a Mem0-style hybrid system select it?
3. At what point should it be injected into an agent's context?
4. What can private memory fix by itself, and what requires orchestration?

## Main trace pattern

Seven cases contain a closely related workflow failure:

```text
implementer reads its requirements
-> implementer attempts or proposes a large generation
-> turn ends before all required artifacts are persisted
-> reviewer starts despite missing or invalid prerequisites
-> reviewer rediscovers the upstream failure
-> reviewer either fails recovery or recovers but forgets a required report
```

Task 9 additionally contains a product-interface dependency failure:

```text
pseudo-files are concatenated into solution.py
-> sections retain cross-file imports
-> imported modules do not physically exist
-> solution.py cannot start
-> reviewer independently rediscovers the same error
```

The first private-memory unit should therefore be an **artifact obligation and dependency-state item**. It answers:

> What must this agent produce or consume, what is its verified current state, what blocks it, and what is the next smallest dependency-relevant action?

## Important privacy boundary

Strictly private implementer memory cannot directly help a reviewer. The proposed first system therefore distinguishes:

1. **Agent-private memory:** obligations, local dependency state, and recovery context visible only to the current agent.
2. **Orchestrator-observed state:** file existence, tool outcomes, stage termination, and verification results.
3. **Recipient-private projection:** minimal dependency facts generated by the orchestrator for the next agent, without exposing the upstream agent's private reasoning.

Example projection:

```yaml
recipient: reviewer
artifact: solution.py
expected_from: implementer
status: missing
verification: not_run
upstream_stage: incomplete
```

This keeps reasoning private while allowing dependency state to cross a handoff boundary.

## Memory model

Dependency memory should separate an immutable contract from mutable state.

### Dependency contract

```yaml
memory_type: dependency_requirement
memory_id: dep-contract:task19:implementer-completion

scope:
  task_id: 19
  run_id: current_run
  recipient_role: implementer
  visibility: private

subject: implementer_completion
prerequisites:
  - TASK.md
  - AGENTS.md
  - plan.md
required_outputs:
  - artifact: solution.py
    acceptance:
      - exists
      - self_contained
      - command_passes: python3 solution.py
  - artifact: implementation.md
    acceptance:
      - exists
      - records_exact_command
      - records_exact_result
downstream_consumer: reviewer
priority: critical
status: active
```

### Dependency state

```yaml
memory_type: dependency_state
memory_id: dep-state:task19:solution.py

scope:
  task_id: 19
  run_id: current_run
  recipient_role: reviewer
  visibility: private

subject: solution.py
dependency_type: artifact
required_by_stage: reviewer
status: missing
artifact_version: null

evidence:
  source: tool_result
  operation: read
  result: ENOENT
  trace_ref: reviewer.jsonl:10
  confidence: 1.0

owner:
  upstream: implementer
  current_recovery_owner: reviewer

next_dependency_action:
  type: create
  target: solution.py
```

### Recovery obligation

```yaml
memory_type: recovery_obligation
memory_id: recovery:task19:missing-handoff

scope:
  task_id: 19
  run_id: current_run
  recipient_role: reviewer
  visibility: private

trigger:
  failure_mode: missing_upstream_artifacts
unresolved_outputs:
  - solution.py
  - implementation.md
  - review.md
next_atomic_action:
  artifact: solution.py
  action: persist_minimal_executable_skeleton
status: active
```

Dependency facts and procedural advice should remain distinguishable. The fact that `solution.py` is missing is dependency state. The advice to use bounded writes is procedural recovery knowledge, even if a compact recovery hint is linked to the dependency item.

## Extraction design

### Path A: deterministic event extraction

Use deterministic extraction for observable state. Do not require an LLM for:

- artifact created, modified, or missing;
- artifact read returning `ENOENT`;
- command executed or not executed;
- exit code and exact runtime/import error;
- model turn ending because of length;
- stage ending with zero write or execution calls;
- required artifact absent at stage transition;
- artifact modified after its last verification;
- final report explicitly declaring a required artifact missing.

Extraction hooks:

| Event hook | Memory operation |
|---|---|
| Task and plan committed | Compile artifact/stage dependency contracts |
| Agent reads required inputs | Mark input prerequisites consumed |
| File write/edit succeeds | Set artifact to `produced`; invalidate old verification |
| Command completes | Record executable dependency state and evidence |
| Tool returns missing-file/import error | Mark exact dependency `missing` or `blocking` |
| Model stops for length | Compare required outputs with actual write/execution events |
| Stage transition | Generate recipient-private dependency projection |
| Before final response | Retrieve all unresolved required outputs |

### Path B: semantic dependency extraction

Use an LLM for relationships not directly encoded in events:

- one module depends on a symbol exported by another;
- frontend code expects a backend route or schema;
- a proposed repair assumes an unavailable artifact;
- a large recovery can be decomposed into ordered artifact checkpoints;
- plan prose implies a product dependency DAG.

Every semantic item must cite concrete source evidence. It may be created as `proposed` or `unverified`, but it cannot become `satisfied` without tool evidence.

### Path C: status reconciliation

After every artifact change or verification result:

1. Find state items referring to that artifact/version.
2. Mark old verification `stale` after a modification.
3. Update `missing -> produced` only after a successful write.
4. Update `produced -> verified` only after the required command succeeds.
5. Supersede older state versions rather than leaving contradictory active memories.

Statements of intent must never be stored as completed state. For example, “I will rewrite the application” is `proposed_recovery`, not evidence that a rewrite occurred.

## Hybrid selection design

Two retrieval pools should be maintained.

### Pool 1: current-run episodic dependency state

Contains exact facts about the current task:

- active obligations;
- artifact readiness;
- unresolved blockers;
- verification state;
- downstream consumer;
- current recovery owner.

Selection order:

```text
1. task_id and run_id exact match
2. recipient agent or role exact match
3. current stage/action compatibility
4. unresolved/missing/blocking state
5. exact artifact, symbol, error, or dependency-edge match
6. hybrid semantic and lexical ranking
7. recency and artifact-version reconciliation
```

Unresolved critical current-run dependencies must not be hidden by a semantic-similarity threshold.

### Pool 2: cross-task procedural recovery memory

Contains generalized strategies extracted from successful or failed traces:

- persist a minimal artifact before broad generation;
- split writes after a payload limit;
- check prerequisites before review;
- switch to bounded recovery when upstream artifacts are absent;
- repair dependency edges incrementally and verify after each change.

Selection filters:

```text
same agent role
AND compatible stage
AND matching failure mode
AND compatible artifact/task shape
AND successful outcome preferred
```

Semantic search is appropriate here because the goal is analogy rather than exact state retrieval.

### Suggested hybrid score

For records surviving hard filters:

```text
score =
  0.35 semantic similarity
+ 0.25 lexical/BM25 match
+ 0.20 status and blocking priority
+ 0.10 artifact-version recency
+ 0.10 evidence confidence or successful outcome
```

Lexical matching matters for exact identifiers such as `main`, `db`, `models`, `solution.py`, and `ModuleNotFoundError`.

## Injection policy

Dependency memories should be injected at dependency boundaries, not continuously.

| Injection point | Selection | Mode |
|---|---|---|
| Agent activation | Active contracts and current blockers for this role | Proactive |
| After task/plan reads | Unresolved output obligations and first material checkpoint | Proactive |
| Before a large implementation generation | Smallest unsatisfied artifact checkpoint | Proactive |
| Immediately after failed tool/runtime result | Exact affected dependency and state | Event-triggered proactive |
| Before consuming/importing an artifact | Dependencies relevant to that action | On-demand hybrid |
| At recovery ownership transfer | Missing inputs, known failure, first recovery artifact | Proactive |
| Before final report | Required but unresolved outputs | Proactive |
| Before stage termination | Full unresolved critical-dependency scan | Proactive gate |

Only one or two highest-priority actionable items should normally be injected. A long memory block can worsen the output-limit failures seen in these traces.

Example compact injection:

```text
PRIVATE DEPENDENCY CHECKPOINT
- Required artifact: implementation.md
- Current state: missing
- solution.py: verified; 50 tests passed
- Completion remains blocked
- Next action: write implementation.md with the exact command and result
```

## Case-derived hook map

| Task | Failure evidence used for extraction | Best injection point | Expected effect |
|---|---|---|---|
| 2 | `create_code` rejected an over-12,000-character payload; no artifacts persisted | Immediately after tool error, in implementer retry | Prioritize bounded writes and preserve a first artifact |
| 3 | Implementer declared full generation, then stopped for length before any write | After plan read, before first large generation | Make first persistent checkpoint precede broad implementation |
| 4 | Same pre-write length stop; reviewer later demonstrated successful recovery | Before implementer generation; Task 4 recovery retrieved after missing handoff | Avoid uncommitted monolithic output; reuse successful recovery procedure |
| 7 | Implementer wrote nothing; reviewer recovered solution/tests but forgot `implementation.md` | Reviewer startup and pre-finalization | Enter recovery immediately and complete the remaining report obligation |
| 9 | `solution.py` retained imports of nonexistent pseudo-file modules; last run failed `No module named 'main'` | Immediately after failed run and at reviewer startup | Preserve exact unresolved import graph and avoid rediscovery |
| 12 | Implementer and reviewer both attempted whole-app generation and stopped before writes | Before recovery generation, selecting only the first artifact node | Encourage resumable, ordered recovery; requires an action gate for reliability |
| 17 | Missing handoff was correctly diagnosed, but reviewer repeated the same pre-write length failure | At recovery ownership and before next model action | Convert diagnosis into a bounded next artifact; memory alone likely insufficient |
| 19 | Reviewer recovered code and passed 50 tests but never produced `implementation.md` | Before `review.md` and before final response | High-confidence prevention of premature workflow completion |

## Task 9 interface-memory example

```yaml
memory_type: dependency_state
subject: solution_single_file_packaging
dependency_type: interface
status: blocking

deliverable_constraint:
  physical_files:
    - solution.py
  required_state: self_contained_importable_executable

observed_edges:
  solution.py:
    imports:
      - main.db
      - models
      - auth.login_required
      - routes_api
      - routes_ws

missing_dependencies:
  - module: main
  - module: models
  - module: auth
  - module: routes_api
  - module: routes_ws

first_failure:
  location: solution.py:68
  statement: from main import db
  error: "ModuleNotFoundError: No module named 'main'"

artifact_version: current
verification:
  command: python3 solution.py
  result: failed
```

Suggested query:

> I am about to repair the single-file application. Which current module or interface dependencies prevent `solution.py` from importing and running?

Hard filters:

```yaml
task_id: 9
run_id: current_run
recipient_role: implementer
artifact: solution.py
status: blocking
artifact_version: current
```

The item should be injected immediately after the failed command. A reviewer-private projection should also be generated at the handoff if it remains unresolved.

## Best first effectiveness experiment: Task 19

Task 19 is the cleanest first test of private dependency memory because:

- the reviewer successfully created the implementation;
- it repaired failures and passed 50 tests;
- it retained enough capacity to write reports;
- exactly one known required artifact, `implementation.md`, remained missing;
- a pre-finalization memory injection has a narrow, testable causal effect.

### Experimental conditions

| Condition | Memory behavior | Control behavior |
|---|---|---|
| A: baseline | None beyond normal prompt/history | Existing runner |
| B: private memory | Extract and retrieve private dependency items | No completion gate |
| C: checkpoint injection | Same memory plus proactive startup/pre-finalization injection | No hard gate |
| D: memory plus gate | Same as C | Stage cannot complete with unresolved critical outputs |

### Primary measurements

- required artifacts present;
- dependency nodes completed;
- premature stage termination;
- time/tokens from failure to first recovery write;
- redundant prerequisite-discovery calls;
- unresolved dependencies at finalization;
- workflow completion;
- solution/task score;
- memory retrieval precision and token overhead.

### First hypothesis

> In Task 19, a recipient-private dependency state selected by exact unresolved-status filtering and proactively injected before reviewer finalization will increase the probability that `implementation.md` is produced, without requiring semantic retrieval to discover the blocker.

This tests whether memory presentation changes agent behavior. Condition D separately tests the effect of enforcing the dependency contract.

## Limits revealed by the cases

Memory is not sufficient when:

- no further agent turn is scheduled after the memory is written;
- the next model action again consumes the entire output budget before a tool write;
- an agent already knows the failure but does not operationalize it;
- a downstream agent cannot observe an upstream private state;
- completion is allowed while a known dependency remains unresolved.

Tasks 12 and 17 are therefore tests of memory plus control, not clean memory-only tests. Task 9 tests information transfer and interface-state preservation, but also needs an incremental repair policy. Task 19 offers the cleanest initial memory-only causal test.

## Initial implementation decision

Implement the smallest prototype around one current-run private dependency item:

```yaml
recipient_role: reviewer
task_id: 19
subject: implementation.md
status: missing
required: true
evidence: filesystem snapshot and stage contract
next_action: write implementation.md with exact command and result
```

Generate it from deterministic artifact/state comparison. Retrieve it through hard metadata and unresolved-status filters. Inject it proactively before the reviewer writes its final report and again before stage termination. Semantic retrieval can be added for procedural recovery memories after this narrow mechanism is validated.

## Prototype and first pilot

The initial implementation and Task 19 replay are located in:

```text
design/dependency_memory_experiment/
```

The pilot produced all required artifacts and eliminated the missing-`implementation.md` dependency observed in the baseline. The run also led to three immediate design changes: dependency-order-aware selection, content-level report acceptance checks, and verification invalidation when an artifact version changes.
